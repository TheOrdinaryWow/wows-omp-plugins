# Visualize — an offline HTML answer

Make the finding easier to understand than the paragraph it replaces. This is an answer artifact, not a new application or a marketing page. OMP has no native inline-HTML rendering surface: deliver a real standalone HTML file, browser evidence and a short chat summary. A browser preview is not an inline thread render.

## Lightweight reply-side route

For a small chart/table/diagram that explains the current reply, use this bounded artifact workflow rather than treating it as a product-site build: no project-wide `DESIGN.md`, separate design-research agents, Lighthouse audit, application scaffold or unrelated redesign. Load the relevant `frontend` hierarchy/type/spacing/state guidance, not its full product workflow. Preserve source correctness, accessibility, draft guard and all four theme/width captures below. This exception applies to a standalone answer artifact, not a landing page, shipped application/dashboard or site restyling. When a static chart is sufficient, native PNG/image delivery through `skill://data-scientist` remains valid; do not manufacture HTML merely because upstream has an inline-page surface.

## Compute → design → build → guard → inspect → deliver

1. **Compute.** Read `skill://data-scientist` for quantitative work and its visualization reference for chart selection, calendar/timezone buckets, partial-window labels and independent cross-checks. Compute at the source when possible (SQL near a database, bounded DuckDB/Polars scans for files), returning only the needed aggregate; use native eval with an appropriate available engine. Do not invent values or install a stack for a qualitative diagram. Keep inputs, query/aggregation, grain, units, missing-row policy and calculation evidence. Every displayed number traces to that computation; distinguish illustrative data explicitly. Name an independent cross-check and discrepancy when available; otherwise disclose its absence instead of inventing a second source.
2. **Design.** Read `skill://frontend` and its relevant references, using the lightweight route above for reply-side artifacts. Preserve required content and choose the chart/table/diagram that answers the question. Define the necessary light/dark tokens inside this HTML, not an application-wide design system. State a short layout contract (primary reading order, responsive behavior, scroll owner) in the work notes. Keep hierarchy and labels, not decorative cards or promotional framing. The title states the finding rather than merely naming the dataset.
3. **Build.** Save one self-contained `.html` file at a real absolute output path outside the installed skill tree. Inline CSS, scripts, SVG, images and any fonts; use system fonts where possible. No CDN, remote library, iframe, external stylesheet/font, fetch, telemetry or network-dependent chart. Prefer semantic markup and inline SVG with a text/table equivalent. Give each chart role a prefixed class or scope it under that chart's parent: a global `.k` reused for KPIs and bar segments can silently alter geometry. Keep the essential answer readable with JavaScript disabled; scripts may enhance interaction but must not supply the only data or figure.
4. **Guard before preview.** Read `skill://frontend/scripts/perfection/check-draft-guard.ts` to resolve the physical frontend skill location supplied by the host. Do not guess a sibling cache path or run a `skill://` URI as a shell filename. Run the dependency-free CLI against the saved artifact:

   ```bash
   bun <physical-frontend-skill>/scripts/perfection/check-draft-guard.ts <page.html> [--json]
   ```

   Exit **0** means clean; **1** means findings (for example decorative accent stripes/outlines, promotional filler, emoji icons, hype badges or vanity-stat forms); **2** means a usage/input failure. Fix the artifact or invocation and rerun until 0. Do not hide/exempt content to force a pass, and do not treat lint as visual approval.
5. **Inspect the real file.** Read `skill://agent-browser`, `skill://visual-qa` and `xd://eval/browser`. Open the actual HTML with the native browser and capture all four states: **light and dark × 390 CSS px and the intended report width** (use 1100 px if none is specified). Set explicit viewport/scale and theme using documented browser emulation. In each view, measure representative geometry for every chart, including the largest bar where applicable, against the plotted values and actual scale/domain/baseline. `value / axisMaximum * plotHeight` applies only to zero-based unstacked linear bars: use transformed endpoints for log/truncated/negative axes, and segment boundaries/totals for stacks. Verify every legend swatch's computed color matches its series and label; inspect first/last axis labels for clipping. Read screenshots and console/errors, top/end content and overflow; exercise controls with keyboard and pointer. Verify the finding, values and labels remain readable with JavaScript disabled and check network diagnostics for unintended requests. Guard lint is not numerical or visual proof. Apply relevant visual-qa evidence rules; after changes rerun the guard and recapture affected states. Never deliver an uninspected page or claim a pass when a required browser/capture surface is unavailable: name the exact unverified criterion.
6. **Deliver.** Give a clickable absolute file path or artifact link, what the page establishes, the calculation/source caveat that matters, and representative screenshot paths. Keep all four captures with their dimensions/theme in the evidence packet. Say **HTML artifact**, not “rendered inline”; do not call nonexistent `show_html_page`, `html_preview` or `html_render` tools. State anything that remains unverified.

## Theme and document contract

OMP does not inject CSS tokens into a file. Define a complete local palette for every token used and declare `color-scheme: light dark`, using `@media (prefers-color-scheme: dark)` for the second palette. Useful names are `--background`, `--foreground`, `--muted`, `--muted-foreground`, `--card`, `--border`, `--primary`, `--chart-1` … `--chart-6`, `--font-sans`, `--font-mono` and `--radius`. Use only the tokens you need; make series distinguishable by labels/shapes as well as color. Do not assume host fonts, a dark background, a preview sandbox or injected confirmation behavior.

Include a UTF-8 charset, meaningful title, document language and viewport metadata. Use a fluid readable container, sensible standalone padding and no ornamental outer card/banner. Keep chart heights intentional; do not stretch SVG text with `preserveAspectRatio="none"`. Axis labels include units, numbers use tabular figures and appropriate precision, and long labels wrap at 390 px. A wide data table may use a clearly labeled local horizontal scroller; the whole page must not overflow. Give keyboard focus and reduced-motion behavior to any controls.

Show a small “How this was computed” block with the query or aggregation and provenance. Name the independent cross-check source, matching scope and any discrepancy; explicitly disclose when no independent source is available (a second calculation of the same data is only a consistency check). Put caveats beside the figure when they change interpretation: missing rows, archived data, small samples or partial windows. Name timezone/calendar boundaries for time buckets and mark an unfinished day/week/month on its own bar/point, using a label plus lighter fill/hatch where useful, not only a subtitle. Empty and failed computations have designed explanatory states, not invented figures or a blank frame.

The offline rule is a build requirement, **not a host-enforced sandbox**. A standalone page runs scripts normally and ordinary links can navigate without an OMP confirmation prompt. Do not embed secrets in HTML or link addresses, trigger navigation automatically, or add network behavior. Intentional source links may remain ordinary links with clear destinations; use `rel="noopener noreferrer"` for new-tab links. Open only task-owned browser tabs and release them after capture.
