# roadmap 使用指南

[English](GUIDE.md) | 简体中文

本指南介绍为什么要用 roadmap、什么时候用、怎样划分放进去的工作，以及一次典型的使用过程。安装步骤、命令列表和已知限制见 [README](README.zh.md)，每个工具操作和文件规则见[参考文档](REFERENCE.zh.md)。

## roadmap 是做什么的

Roadmap 把一个仓库的目标和交付记录以 Markdown 形式保存在 `docs/roadmap/` 下，由代理通过专用工具维护。单个计划回答不了的问题，由它来回答：

- 我们为什么做这件事，为什么是现在？
- 这一轮承诺了什么，接下来做什么？
- 哪些已经得到证明，哪些还欠着？

新开的会话读一遍就能从上一个会话停下的地方接着做，你不用再把项目讲一遍。

### 分工

| 组件 | 负责 |
| --- | --- |
| Roadmap | 目标、阶段边界、依赖、完成标准、延后的工作、实际结果。 |
| Prometheus | 一件工作怎么做：调研、设计、写计划。 |
| Atlas | 执行已批准的计划：委派、证据、关口、交付。 |

Roadmap 依赖 [adr 插件](../adr/README.zh.md)，阶段引用和关联的架构决策由它保存。Prometheus 和 Atlas 来自 `omo-prometheus` 插件。没有它 roadmap 也能用，但下文与计划相关的功能需要它。

```mermaid
flowchart LR
    R[Roadmap：阶段与完成标准] -->|交接| P[Prometheus：计划]
    P -->|已批准的计划| A[Atlas：执行与证据]
    A -->|完成提醒| R
```

Roadmap 从不保存实现计划。计划存放在 Atlas 的计划包里，roadmap 需要展示某个阶段有哪些计划时才去读取。

### 它在计划之间补上了什么

单个计划内部的工作，Prometheus 和 Atlas 已经在跟踪。Roadmap 负责从一个计划到下一个计划之间的这些事：

- 为什么下一步是这一步；
- 上一个阶段实际交付了什么、与承诺有什么出入、留下了哪些限制；
- 你即将批准的计划是否仍然符合本轮的约束；
- 哪些发现已经变成承诺，并在路线图里有了归属；
- 新会话应该从哪里接着做。

### 为什么不用 GitHub Projects 或 Issues

所有内容都是仓库里的文件，所以 roadmap 不依赖任何托管服务，并且直接接入代理工作流：交接、关闭时的证据检查、提醒。它需要本地 Git 仓库，但不需要远程仓库。不是 Git 工作树的目录不受支持。如果想在那里使用，`git init` 是你可以自己选择的做法，roadmap 不会替你执行。

### 它保证什么，不保证什么

- 关闭阶段时，插件检查每条当前标准是否都有证据，但不检查证据是否属实，所以代理必须真的运行它所报告的检查。
- 已关闭的阶段和轮次会被冻结，已关闭的阶段永远不会重新打开。
- 计划完成不会自动关闭阶段。阶段能否关闭由你或代理判断。

## 什么时候适合用 roadmap

计划的数量不是好的判断依据。更该问的是：这项工作是否需要在多次执行之间保留目标、顺序、决策和未了结的事项？典型场景：

### 大型新项目

问题：前几个计划都很顺利，之后没人记得最初构想里哪些已完成、哪些延后、哪些放弃了。

用法：运行 `/init-project`，描述第一轮的目标和它的阶段。后面的轮次保持粗略。每个阶段都写上可检查的标准，这样每个阶段都有明确的终点。

### 迁移、升级或替换系统

问题：兼容、切换、回滚、下线旧路径要分很多步完成，漏掉一步就会在后面出问题。

用法：把兼容和回滚各自做成带标准的阶段。把"旧路径已移除"写进最后一个阶段的标准。下面的[完整示例](#一个完整示例)就是这种情况。

### 长期的产品迭代

问题：每一轮的目标不同，延后的想法越积越多，却没有去处。

用法：每一轮对应一个产品目标。用 `/roadmap plan-round` 提前起草下一轮，只把这一轮写详细。延后的想法记成 TODO，指向它所属轮次的某个阶段，或者写明触发条件。

### 技术债、性能和可靠性专项

问题："让它更快"没有尽头，进展也难以证明。

用法：第一个阶段做基线测量。之后的阶段写可度量的标准和明确的停止条件。决定不做的事，在关闭该轮时记为 `wontfix` 并写明原因，它会出现在该轮的已知限制里。

### 安全整改或审计发现的修复

问题：需要知道哪些已修复、哪些已验证、接受了哪些风险。

用法：把发现分组成阶段，每个发现或每一类发现对应一条标准，并写明验证方法。接受的风险连同原因一起记录。这份记录说明你做了什么，但不构成合规认证。

### 从调研到工程

问题：调研结束了，却没有人能找到相应的决策，实现只能建立在假设之上。

用法：把调研做成一个阶段，标准是一个有依据的决策，通常是一份 ADR。把这份 ADR 关联到该阶段：关联的 ADR 仍处于提议状态时，阶段无法关闭；依赖它的实现阶段要等它关闭后才能开始。

### 接手旧项目，或长时间中断后重新开始

问题：你不记得现状，也没有书面记录。

用法：运行 `/init-project`，以今天的代码为基线，写下下一轮的目标。从未发生过的轮次不必补写。

## 什么时候不该用

- 一个会话就能做完的修复。
- 没人承诺要继续的一次性实验。
- 繁忙的日常分诊队列。每条 TODO 都必须指向一个阶段或写明触发条件，适合记录承诺，拿来当收件箱反而碍事。
- 多个相互独立的产品或仓库。每个 Git 根目录只有一份路线图、一个活动轮次，无法跨仓库协调。

路线图之外的工作不需要阶段。如果你提出的请求与某个未关闭的阶段重叠，并且代理注意到了，它会针对该阶段在每个会话中问一次：使用路线图、记为自由工作，还是视为无关。自由工作只在该阶段的日志里加一行，不代表满足了任何标准。

## 轮次、阶段和计划

### 轮次

一轮有一个结束时能判断成败的目标，例如"首批用户能完成核心流程"。同一时间最多一个活动轮次。可以提前规划未来的轮次：最近的一轮写详细，其余保持粗略。关闭一轮时，记录目标是否达成（`achieved`、`partial`、`not_achieved` 或 `cancelled`）并写一段摘要。格式 2 的仓库要求必须填写（见[仓库格式 2](#仓库格式-2)）。

### 阶段

阶段是一个可以单独验证的结果，例如"用户能登录并看到自己的数据"。按层次切分（"先写后端，再写前端，最后写测试"）效果很差，因为其中任何一部分单独都无法判断是否完成。

一个阶段通常有两到六条完成标准，每条写明必须通过什么、怎么验证。只有真正的前置条件才声明为依赖。依赖没有关闭时，阶段无法开始。

### 计划

计划是达成阶段部分或全部标准的具体路径，一个阶段可以由多个局部计划共同完成。每个计划用一行写明自己负责的标准：

```text
Roadmap criteria: DC1, DC3
```

Prometheus 在计划提出时、请你批准之前检查这一行。绑定了阶段的计划必须有这一行，至少列出一个 ID，并且只能列出该阶段当前已有的 ID。阶段交接会显示之前的计划已经覆盖了哪些标准，下一个计划可以接手剩下的部分。

如果一开始就知道某个阶段包含几块庞大且相互独立的内容，就拆分阶段。一个阶段多个计划，适合各部分天然有先后顺序的工作，也适合某些内容未通过之后的补救或重新规划。

### 规模的经验值

| 情况 | 建议 |
| --- | --- |
| 每轮的阶段数 | 三到八个。超过十个左右，通常说明这一轮包含了两个目标。 |
| 总共五到八个计划 | 一轮就够。 |
| 更多 | 一个活动轮次，加一个写详细的计划中轮次，之后的轮次保持粗略。 |

## 一个完整示例

你要替换一套认证系统。这需要六个以上的计划，所以分成两轮。计划中的轮次需要格式 2（见下文）。

R1 轮，"验证新系统能够取代旧系统"：

| 阶段 | 结果 | 标准示例 |
| --- | --- | --- |
| S01 | 记录当前行为与约束 | 旧系统的每一条登录路径及其调用方都已列出。 |
| S02 | 新的登录路径端到端可用 | 测试用户通过新路径登录并访问受保护的数据。 |
| S03 | 完成回滚演练 | 在预发布副本上切回旧路径成功，并记录耗时。 |

R2 轮，"安全切换"：

| 阶段 | 结果 |
| --- | --- |
| S04 | 新旧账号的身份映射 |
| S05 | 小范围用户切换 |
| S06 | 全量切换并移除旧路径 |

你用 `/init-project` 创建 R1，用 `/roadmap plan-round` 起草 R2，再让代理把 S04 到 S06 加进 R2（代理会调用 `roadmap_stage`，参数为 `action: "add"`、`round: "R2"`）。做 S02 时，代理发现密码重置在新系统里的行为不同。这项工作确实要做，但不属于 S02，于是代理用 `roadmap_todo` 记下一条指向 S05 的 TODO。关闭 R1 时，这条未关闭的 TODO 因为指向计划中轮次的阶段，会自动移入 R2 的 TODO 文档，并保持原来的 ID。之后它会出现在 S05 的交接内容里。

S02 可能需要两个计划：一个做登录后端，声明 `Roadmap criteria: DC1`；稍后一个做客户端，声明 `Roadmap criteria: DC2, DC3`。每条标准都有来自任一计划的通过证据后，S02 就可以关闭。

## 工作流程，一步一步来

1. 初始化。运行 `/init-project`，已有项目同样适用：描述今天的基线和下一轮的目标。确认预览之前不会写入任何内容。
2. 划分阶段。把每个阶段写成可验证的结果，附上标准和真正的依赖。用 `/roadmap plan-round` 起草后面的轮次，保持粗略。
3. 选下一个阶段。`roadmap_status` 和代理每个回合看到的状态，会列出哪些阶段现在可以开始，其余阶段在等哪些未关闭的依赖。这些信息每次都从文档推算，不额外存储，直接问代理即可。
4. 开始阶段，然后做计划。开始阶段会把会话绑定到该阶段并返回交接内容，接着用 `/prometheus` 做计划。交接内容包括：本轮的目标、约束和非目标；它所依赖或接续的阶段实际交付了什么、有哪些偏差；未关闭的 TODO；引用的 ADR；以及该阶段已有的计划和它们覆盖的标准。新计划在 `Roadmap criteria:` 这一行里声明自己负责的标准。
5. 工作中把变化放到对应的地方。

   | 变化 | 去处 |
   | --- | --- |
   | 阶段的范围或标准 | 带原因的阶段修订（`amend`）。 |
   | 以后再做的工作 | TODO。 |
   | 架构决策 | ADR，通过 adr 插件。 |
   | 不相关的小事 | 自由工作。 |

   如果阶段在计划批准之后发生了变化，roadmap 和 Atlas 会显示一条提示，方便你重新检查计划。执行不会暂停。
6. 处理执行中的发现。Atlas 释放计划之前，每个范围之外的发现都必须有处置：记为 Roadmap TODO、标为重复，或不予处理。最终报告会列出这些发现供你审阅。
7. 评估能否关闭。计划完成后，执行它的会话会收到一条提醒，显示所有计划对每条标准的覆盖情况、哪些计划尚未完成，以及偏移提示。关闭需要每条当前标准都有通过的证据，证据可以来自任一计划。关联计划尚未完成时也可以关闭，roadmap 会给出警告，并把这一点记入阶段 Outcome 的 Deviations。
8. 关闭这一轮。所有阶段关闭或放弃后，运行 `/roadmap close-round`。记录目标的达成结果，把每个剩余的 TODO 处理为 `resolved`、`wontfix` 或 `carried`，然后决定下一轮。`/roadmap new-round` 激活计划中的轮次之前，会再和你确认一次它的目标。

## 日常可以这样说

大部分时候你用自然语言和代理交流。下面这些请求效果不错：

- "读一下路线图，告诉我现在哪些阶段可以开始，并根据目标和风险推荐下一个。先不要写计划。"
- "开始 S04。在详细规划之前，先检查本轮的约束、前置阶段实际交付了什么，以及当前的代码。"
- "这个计划做完了。对照完成标准评估 S04 能否关闭，列出还没被证明的部分和应该延后的部分。"
- "关闭本轮之前，把轮次目标和各阶段实际交付的内容对比一下，告诉我目标是否达成。"

初始化和轮次级别的变更（规划、开启、放弃、修改目标日期）始终需要你明确运行命令并确认预览，代理无法自行执行。升级到格式 2 也要等你同意：只有你在对话框里选"是"，或者运行 `/roadmap upgrade`，才会写入。

## 仓库格式 2

计划中的轮次、目标日期和轮次目标结果需要仓库格式 2。从不使用这些功能的仓库会逐字节保持格式 1。

- 在格式 1 的仓库里，每次启动或切换到一个会话时，主会话都会询问是否升级。选"是"立即升级；选"否"只关闭这个询问，不改动任何内容。任务需要格式 2 时，代理也可能询问你。
- 随时可以用 `/roadmap upgrade` 升级。没有对话框时（无界面或无头模式），你会收到一条提到该命令的提示。
- 升级之后，**roadmap 0.2.3 及更早版本将无法读取该仓库**。已关闭的历史不会被改写。
- 在格式 1 的仓库里关闭一轮时，会先询问是否升级。跳过则这一轮不记录目标结果直接关闭；升级则需要记录。格式 2 始终必须填写。

如果还有别人在同一个仓库里使用 roadmap 0.2.3 或更早版本，请先让他们更新插件，再进行升级。

## 局限，以及 roadmap 刻意不做的事

Roadmap 刻意不提供看板、故事点、速度统计、自动排期、里程碑实体，也不与问题跟踪器同步。同一时间只允许一个活动轮次，不会重新打开已关闭的阶段，也不会因为计划完成就关闭阶段。它需要本地 Git 仓库。它检查证据是否存在，证据是否属实取决于运行检查的人。
