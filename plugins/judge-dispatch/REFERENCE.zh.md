## 代理发现

候选代理来自实时 `task` 工具描述中的代理列表。列表缺失、无法解析或为空时，插件跳过判定。插件写入的代理名都会再经过 `task` 工具校验。请求是否只读，由 OMP 对所请求代理自身工具的判定决定。只读请求只能改派给工具也是只读、且 `spawns` 未授予任何子代理派发权限的代理。即使当前会话用不了这项权限，获授权的代理也不能成为改派目标。原代理仍是候选项，因此只要有一个合格的改派目标，就会交给判定模型选择。

插件使用 OMP 校验后交给 `tool_call` 的 `agent` 值，其中也包括 OMP 补上的默认值。改写时可以保留这个值。如果校验后的任务项仍然没有 `agent`，插件会从实时工具描述中查找默认代理。无法识别默认代理时，调用原样交给 OMP。确定了默认代理后，插件按同一权限规则判断，并以该代理的配置作为模型档位和思考级别调整的起点。

你在会话中标记的模型代理（如 `m1`）只供显式调用。插件将它们排除在自动路由之外，也不对这些调用做判定、调整模型档位或思考级别，或记录重试和升级。如果已安装的代理与标签同名，OMP 优先使用已安装的代理，插件照常路由。

只要评级能改变某些东西，即使只有一种代理类型可选，judge 也会评估难度：开启了 `judgeEffort` 且条目没有设置 `effort`，或者 `modelTiers` 中有条目适用于最终使用的代理。如果只有部分候选代理配置了档位，插件会先选择代理，仅在选定代理有档位时才询问难度。

## 模型档位

`modelTiers` 是以逗号分隔的 `[<agent>.]<routine|demanding>=<selector>` 条目列表。任何格式错误或重复的条目，以及 `standard` 条目，都会使整个设置无效，此时插件原样保留所有调用。对于任务最终使用的代理，插件先查找 `<agent>.<difficulty>`，再查找 `<difficulty>`。

档位的展开方式如下：

- `@<role>`：展开后的 `modelRoles[role]` 选择器，后接 `retry.fallbackChains[role]`；角色没有配置链时后接 `default` 链。
- `provider/model[:level]`：该选择器，后接 `default` 链。

在 `tool_call` 阶段，插件根据当前项目的 OMP 设置和已启用模型检查档位：角色必须存在，回退链必须是不含提供商通配符的选择器列表，并且必须有已启用的模型能够解析。未通过检查的档位会保留代理的模型，并在状态行中写明原因。只有当档位第一个解析成功的模型就是代理自身选择器解析到的模型，并且思考级别也相同（选择器显式的 `:level`，没有时使用代理的 `thinkingLevel`）时，档位才不做任何改变，此时思考级别调整仍可能生效。档位指定代理自身模型但级别不同时，会应用该级别，不再做思考级别调整。只解析出一个选择器、自身没有回退链的档位不会被拒绝；OMP 会用代理自己角色的链重试它，即回退到代理的模型一侧。

## 思考级别调整

OMP 按以下顺序决定子代理的思考级别：任务的 `effort`，然后是模型所解析的选择器上显式的 `:level` 后缀，最后是代理定义的 `thinkingLevel`。`effort`（`lo`、`med`、`hi`）会映射到模型支持的最低、中间或最高级别，所以写入它会抹平精心配置的级别，例如代理的 `xhigh`。插件从不写入 `effort`。

开启 `judgeEffort` 且条目没有 `effort` 时，插件按以下步骤计算调整：

1. 基准是 OMP 在没有 `effort` 时会使用的级别：第一个能解析到已启用模型的选择器上的 `:level`，没有时使用代理的 `thinkingLevel`。没有基准，或者基准为 `auto`、`inherit`、`off` 时不做调整。
2. 基准先按模型支持的级别收敛，与 OMP 应用级别时的做法一致。
3. routine 评级下调一个受支持的级别，demanding 评级上调一个受支持的级别。最低受支持级别之下、最高受支持级别之上都不再调整，所以调整永远不会降到 `off`。
4. 结果再按 `task.maxEffort` 收敛。OMP 只对 `effort` 应用这个上限，所以插件自己应用它。会被上限抵消的上调直接放弃。

级别的顺序和受支持的级别来自 OMP 自身的思考级别工具函数和模型注册表。派生时，插件为解析成功的那个选择器添加或替换 `:level` 后缀，选择器本身和其他模式都保持不变。OMP 把这个后缀视为显式指定，所以它优先于代理的 `thinkingLevel`。档位切换了模型时，不做思考级别调整。

## 重试与升级记录

父代理用同一个 `name` 重新派发任务，也可以沿用插件生成的名字。插件按派发时的任务名保存记录，因此 `Lane-1` 和 `Lane-2` 分别记录。以下两种结果会提高下次派发的难度。

- 升级：子代理最终输出的第一个非空行恰好是 `ESCALATE: deep-high`。下一次派发按 `demanding` 处理。
- 子代理应用了 `routine` 档位或下调了思考级别，之后以中止、非零退出码或错误结束。下一次派发按 `standard` 处理。

`task` 的 `tool_execution_end` 通过任务项的位置标识同步结果。调用报错时，某个同步任务项如果已经应用 `routine` 档位或下调过思考级别，且结果中没有该项的记录，就计为失败。其他结果行只对应各自的任务项。后台任务首次出现在 `tool_execution_update` 时，插件按子代理 ID 和派发时间关联父会话中的作业。若任务首次出现在调用结果中，就在调用结束时关联。作业结束时，插件读取终态和交付的 `<task-result>` 文本中的 `<output>` 或 `<preview>`。只有符合路由条件的任务才会留下重试记录。

下次派发符合路由条件的同名任务时，插件保留请求的代理，跳过判定，按记录的难度应用档位或调整思考级别。只有返回提升后的路由才会用掉这条记录。跳过路由、超时或失败放行时，记录会留给后续派发。最多保留 256 条重试记录，超出时先移除最早的一条。

## 从判断到派生

OMP 的 `before_subagent_spawn` 事件给出派生键，但不提供工具调用 ID 或任务项序号。插件只在恰好有一项待派发任务匹配时才使用它的决定。已知宿主分配的子代理 ID 时按 ID 查找，否则按任务名和可能的重名后缀查找。例如，`Lane` 和 `Lane-2` 都可能匹配派生键 `Lane-2`。如果多个任务项匹配，插件会放弃这些项的档位和思考级别调整，也不会把这些派生记为已下调。既没有任务名又没有已知 ID 的任务项可能匹配任何派生键。

未命名任务需要应用档位或调整思考级别时，插件会写入 `<agent>-<8 hex>`。派生时，代理和起始模型必须与预期一致，重算后的思考级别也必须与原决定一致。调整生效时，OMP 会在子代理实际使用的模型旁显示路由说明。

改写只会改动：开启 `routeAgent` 时的 `agent`，以及档位或思考级别调整需要时的 `name`。

### 已知限制

- 同名调用并发时，可能跳过派生时的调整。判定超时的调用仍算作可能的匹配项，直到插件能确定哪个子代理由它派生，或宿主报告调用结束。
- 直接 SDK 调用如果被其他扩展拦下，或在执行前被宿主拒绝，可能没有 `tool_execution_end` 事件。留下的任务名可能使后来的同名任务跳过调整。没有结束事件的直接调用也可能无法在同步任务失败后提高重试难度。
- 每个会话最多保留 256 条派发记录，超出时移除最早的一条。如果移除的记录还有任务未派生，该任务可能随后才启动，这个会话会跳过其余所有派生调整。移除记录也可能丢掉重试提级所需的结果。
- 如果 SDK 会话使用私有代理注册表和独立的扩展根目录，同一个代理名可能在会话中解析到与插件所见不同的定义。插件的只读检查结果因此可能与 OMP 实际派生的代理权限不符。
- 判定尚未返回时，如果有人修改了代理定义，OMP 会在派生时使用修改后的定义。
- 其他扩展可能在 judge-dispatch 处理完调用后给任务改名。如果新名字与一条待应用的路由匹配，且代理和起始模型也相同，改名后的任务就可能用上那条路由的档位。
- SDK 调用方如果在上一次调用尚未结束时复用同一个工具调用 ID，可能覆盖派发记录，导致后续事件关联到错误的调用。
- 同名的两次重试如果同时进行，且都在记录被消耗前读到它，就可能用上同一条升级记录。
- 使用私有代理注册表的 SDK 会话中，后台任务的失败不会留作重试依据。插件通过全局注册表查找父会话，才能找到它的后台作业。

跳过派生调整时，任务按 OMP 为所选代理解析的模型和思考级别运行。选择代理时仍遵循同一套权限规则。

如果宿主在 `before_subagent_spawn` 中提供工具调用 ID，插件就可以直接区分不同调用，无需按任务名匹配。任务项序号则可以区分同一批次中的各项。

## 原生逐项模型与分阶段任务

开启 OMP 的 `task.perCallModel` 设置后，task 条目可以自带 `model`。插件对这样的条目保持代理、选择器和 effort 原样：不做代理判断，不询问难度，不套用档位、思考级别调整或重试提升，其他派发中同名的待应用决策也不会作用到它身上。

`model` 是空字符串或空列表时视同没有指定模型，与 OMP 的处理一致，这样的条目照常路由。

开启 `task.steps` 后，条目可以用 `steps`（按顺序执行的若干阶段）代替 `task` 给出任务内容，每个条目必须且只能有其中一个。判定模型把各阶段合成一份编号列表来判断，`steps` 数组原样传递。

路由判断会解析当前的本地会话，并把它的费用闸门传给 `resolveJudge`，因此会计入 `session.maxCost`，达到上限后被拒绝；用量仍照常记账。找不到本地会话时，插件按原方式判断。

## 超时与失败

路由最多等待八秒，并且总会在会话工具调用处理超时前至少一秒结束；如果已经没有时间，就跳过路由。请求、凭据和用量记录都经由 OMP 的 `judge` 角色处理；插件不保存密钥，也不改动进程环境变量。

## 不使用终端界面时

路由、思考级别调整和档位在 RPC、ACP 编辑器、SDK 和无界面模式下都一样有效。RPC 客户端以通知帧接收工作提示和状态行；ACP 编辑器可能只把它们写进日志。没有 UI 时不显示这些提示。插件没有对话框，也没有命令。

通过 `eval.agent()` 或 `workpool()` 启动的子代理不会被路由，因为 OMP 的 `before_subagent_spawn` 钩子只能更改子代理的模型，不能更改代理类型。

## 状态

插件不在会话文件中保存路由状态，也不发布插件状态快照。待应用的档位和思考级别调整，以及重试与升级记录都只保存在当前进程中；重启后丢失。清单中已不再声明的已存设置会被忽略，并在每个会话中警告一次，提示改用 `modelTiers`。旧版本的对话记录仍可正常渲染和过滤。
